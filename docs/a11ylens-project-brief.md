# A11yLens Project Brief

## 1. Purpose

A11yLens extends the existing `jupyterlab-a11y-checker` project with
context-aware model-assisted accessibility analysis.

The existing deterministic checker remains the foundation of the system.

The primary required semantic case is:

- image alternative-text quality

The project investigates whether notebook structure can provide useful
context for:

- identifying semantically weak alternative text,
- generating improved alternative-text suggestions,
- validating generated suggestions before they are shown to the notebook author.

Model-assisted findings are recommendations and should not replace
deterministic accessibility checks or be treated as definitive WCAG violations.

---

## 2. Existing Repository

The upstream repository already contains three main packages:

- `packages/core`
  - shared notebook parsing and accessibility analysis logic

- `packages/extension`
  - JupyterLab user interface and interactive remediation functionality

- `packages/cli`
  - command-line interface built on the shared core functionality

For A11yLens development, focus primarily on:

- `packages/core`
- `packages/extension`

The CLI should remain compatible with shared core behavior where practical,
but it is not the primary interface for the A11yLens project.

The existing repository is the source of truth for current abstractions,
package boundaries, naming, and behavior.

Do not create new A11yLens-specific abstractions until the repository has
been inspected for equivalent existing functionality.

---

## 3. Required Scope

The required end-to-end workflow should support:

- images embedded in notebook Markdown/content,
- supported static image outputs generated by code cells,
- missing alternative text,
- empty alternative text,
- nonempty but semantically weak alternative text,
- notebook context selection,
- semantic analysis,
- remediation generation,
- validation,
- JupyterLab author review.

The primary workflow focuses on informative images.

Automatic determination of whether an empty alt value represents a decorative
image is outside the required implementation.

---

## 4. Secondary Scope

Only after the required image workflow is working:

- link-description quality

Stretch goal:

- table-caption quality

Out of scope for the required implementation:

- arbitrary interactive widgets,
- arbitrary dynamic outputs,
- complex mathematical accessibility,
- full program-dependency analysis,
- semantic dependency tracing across an entire notebook,
- automatic decorative-image classification,
- embedding-based or model-based retrieval in the first context-selection implementation.

---

## 5. Architectural Responsibilities

The implementation should preserve the existing repository architecture where
possible while supporting the following responsibilities.

### Notebook Access

Provide access to:

- cell order,
- cell type,
- source content,
- headings,
- notebook location information,
- supported outputs,
- accessibility-related content.

Prefer extending existing core notebook representations rather than creating a
parallel notebook model.

### Structural Accessibility Checking

Existing deterministic checking remains responsible for accessibility issues
that can be reliably identified using explicit rules.

Examples include:

- missing alt text,
- empty alt text,
- heading structure,
- table structure,
- other currently supported deterministic rules.

Structural findings must remain available even if model-assisted functionality
is unavailable.

### Model-Assisted Candidate Routing

Supported findings or notebook content may enter model-assisted processing.

Two primary image states are important:

#### Missing or empty alt text

```text
candidate
-> context selection
-> remediation
-> validation
-> author review
```

#### Nonempty alt text

```text
candidate
-> context selection
-> semantic analysis
-> if insufficient: remediation
-> validation
-> author review
```

If the existing nonempty alt text is considered sufficient, remediation is not
generated.

Do not force these responsibilities into a new "router" class if existing
repository abstractions already provide an appropriate place for this logic.

---

## 6. Context Selection

The initial structure-aware strategy should use simple, explainable notebook
signals.

Priority order:

1. candidate and current cell
2. nearest preceding section heading
3. nearby Markdown within the same section
4. associated or potentially related code
5. additional nearby content within the same section if the context budget allows

### Code Relationships

For a static image output produced directly by a code cell:

- the source code from the same code cell is directly associated with that image.

For an image embedded in Markdown:

- nearby code may be considered potentially related,
- but the relationship is heuristic and should not be treated as guaranteed.

Do not implement complete dependency tracing in the initial version.

### Context Budget

Context input should have a configurable limit.

Possible measures include:

- tokens,
- characters,
- another practical provider-supported measure.

When the budget is exceeded:

- retain higher-priority context first,
- shorten or omit lower-priority material.

Do not include unrelated notebook content merely because unused context capacity
is available.

---

## 7. Context Strategies

The implementation should allow the semantic pipeline to run using different
context strategies.

Required comparison strategies:

### Minimal Context

Candidate plus essential local information.

### Fixed-Window Context

Candidate plus a fixed number of neighboring cells.

### Structure-Aware Context

Context selected using notebook structure and the priority rules above.

### Largest-Practical Context

A substantially larger portion of the notebook when supported by the selected
model.

Where practical, these strategies should use the same downstream semantic
analysis pipeline.

---

## 8. Context Representation

Use a shared provider-neutral representation between notebook processing and
model communication.

A conceptual example:

```json
{
  "candidateType": "image-alt-text",
  "cellIndex": 13,
  "existingText": "graph",
  "sectionHeading": "Quarterly Revenue Analysis",
  "nearbyMarkdown": "The following visualization compares revenue across four quarters.",
  "relatedCode": "plt.plot(quarters, revenue)",
  "visualContent": "associated image"
}
```

This is a conceptual schema, not a requirement to create this exact interface.

Prefer adapting existing repository types when suitable.

The representation should preserve enough information to support:

- candidate identification,
- notebook location,
- selected context,
- existing accessibility content,
- model input construction,
- later evaluation.

---

## 9. Model Interface

The primary image workflow should use a multimodal vision-language model when
direct image inspection is needed.

The core implementation should remain provider-neutral.

Potential providers include:

- NRP-managed multimodal Qwen models,
- NRP-managed multimodal Gemma models,
- Gemini Flash models.

Do not hard-code notebook analysis or context-selection logic to one provider.

Provider-specific concerns should remain behind the model interface.

The exact model can be selected based on:

- image-input support,
- structured-output reliability,
- context capacity,
- availability,
- latency,
- usage cost.

---

## 10. Semantic Analysis and Remediation

For nonempty alt text, semantic analysis should determine whether the existing
description is sufficiently informative for the image and selected notebook context.

The initial implementation may combine semantic analysis and remediation into
one model request.

Conceptual output:

```json
{
  "semanticConcern": true,
  "reason": "The existing alternative text identifies the content as a graph but does not describe the main trend.",
  "suggestedText": "Line chart showing quarterly revenue increasing from Q1 through Q4."
}
```

Generated remediation should:

- be grounded in available visual and notebook information,
- communicate the important result,
- avoid unsupported details,
- remain concise enough for practical accessibility use.

---

## 11. Validation

Generated remediation should be validated before author review.

### Deterministic Validation

Check items such as:

- expected fields exist,
- expected types are correct,
- suggestion is nonempty when required,
- structured output can be parsed,
- configured formatting or length constraints are satisfied.

Malformed model output should not be presented as a valid recommendation.

### Model-Assisted Validation

Use a separate model request to evaluate:

- groundedness,
- context consistency,
- informativeness,
- conciseness,
- unsupported content.

The same underlying model may be used for generation and validation using
different prompts.

If validation fails:

- optionally allow one controlled revision,
- otherwise mark the recommendation for additional author review.

Avoid open-ended generation/validation loops.

---

## 12. JupyterLab Author Review

Model-generated recommendations must remain editable and reviewable.

The author should be able to inspect:

- existing accessibility content,
- semantic concern,
- proposed remediation,
- validation status.

The author should be able to:

- edit,
- accept,
- reject.

Do not automatically modify notebook content without author approval.

---

## 13. Evaluation Support

The implementation should preserve enough information to compare:

- context strategy,
- semantic result,
- remediation output,
- validation result,
- model input size,
- token usage when available,
- latency,
- request count,
- failed or malformed responses.

Avoid designing evaluation infrastructure so tightly around one provider that
other compatible models cannot be tested.

---

## 14. Development Order

Unless repository structure suggests a better sequence:

1. understand the existing implementation
2. map existing image-alt and AI remediation behavior
3. verify or extend image candidate extraction
4. establish a minimal provider-neutral model call
5. implement minimal-context processing
6. implement fixed-window context
7. identify or introduce the smallest context-strategy abstraction
8. implement structure-aware context selection
9. implement semantic analysis/remediation
10. implement deterministic validation
11. implement model-assisted validation
12. integrate results into the existing JupyterLab UI
13. add evaluation/logging support
14. refine tests and architecture

Prefer one working vertical slice before adding more advanced functionality.
